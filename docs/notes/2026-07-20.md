## Session forking: true handoff semantics (pi/claude, live-verified)

Executed `docs/plans/2026-07-20-session-forking-handoff.md`. Handoff now
forks the native session where the CLI supports it:

- `_command_for_prompt` handoff branch → `_fork_command(session_id, prompt)`;
  base returns None (no fork) → one-shot fallback. pi:
  `pi --mode json --fork <src> -p`; claude:
  `claude --resume <src> --fork-session -p ...`; codex/kimi: None.
- New run binds the forked session id from the wire via existing `_bind_session`.

### Live proof — controlled experiment

First probe iteration was flawed: the codeword rode the handoff context, so
every CLI "passed" (envelope knowledge, not inheritance). Fixed design:
handoff context carries NO codeword; the receiving run can only know it via
session inheritance. Results (this machine):

- pi: fork → NEW session `019f7f62-41f1…` (≠ src), codeword recited ✓
- claude: fork → NEW session `81242f64-…` (≠ src), codeword recited ✓
- codex: one-shot (no native fork), codeword NOT found — honest fallback ✓
- kimi: one-shot, codeword NOT found ✓

`tests/external/test_hlp_session_continuity_real_cli.py` now asserts both
directions (fork inheritance for pi/claude, no inheritance for codex/kimi);
offline tests pin fork commands, new-session binding, and fallbacks.

Capability matrix is documented in README; when codex/kimi ship native fork
support, `_fork_command` is the single extension point to enable it.
